- 設計そのものは `docs/design.md`。このファイルには「なぜそうなっているか」「何を踏んだか」を書く。

## 追記1: S1 の結果と、GL レンダラでガラスが断片になる件（2026-09-24）

### A. S1 の結論

snapshot の中で「`render_texture` → CPU → 自前の GL → `GdkGLTexture`」を行う方式は**成立する**。
パネル 2 枚で、スクロール中のガラスの CPU 時間は 1 フレームあたり平均 1.4〜1.5 ms。60fps を保った（Vulkan / GL / X11）。
静止中は snapshot 自体が起きず、前景だけが変わるときはキャッシュで 0.02 ms。数値の全体は `spikes/s1-full-renderer/README.md`。

### B. 症状

`GSK_RENDERER=gl`（X11 では GL が既定なので `GDK_BACKEND=x11` でも同じ）で、ガラスのカプセルが**約 2 倍に拡大された左上の断片**として表示された。
右端は、どのパネルも同じ x 座標で切れていた。Vulkan レンダラでは正常だった。

### C. 切り分け

| 条件 | 結果 |
|---|---|
| Wayland・Vulkan | 正常 |
| Wayland・GL | **壊れる** |
| X11・Vulkan（`GSK_RENDERER=vulkan` を明示） | 正常 |
| X11・GL（既定） | **壊れる** |

→ X11 ではなく **GL レンダラ**が変数。

### D. 原因

`capture_and_blur()` は snapshot の最初に自分のコンテキストを current にしてから、`gsk_renderer_render_texture()`（窓のレンダラ）を呼んでいた。
GL レンダラはここで自分のコンテキストを current にして描き、**そのまま戻る**（ダウンロードも同様）。
その後の `glTexSubImage2D`・ぼかし・ガラスのパスは、GTK のコンテキストで実行されていた。

- テクスチャとプログラムは共有グループ内で共有されるので、エラーは出ない。
- **FBO と VAO は「コンテナオブジェクト」で共有されない**。GTK のコンテキストでは同じ番号が別物（または無効 = 既定の framebuffer）になり、ガラスは出力テクスチャに描かれなかった。
- 画面に出ていたのは、出力テクスチャに残っていた別の内容だった。

### E. 修正

取り込み（`render_texture` とダウンロード）の直後に `gdk_gl_context_make_current (self->ctx)` を呼ぶ。性能への影響は測定誤差の範囲だった。
**一般則: GTK の描画 API を呼んだら、自前の GL を続ける前に必ず自分のコンテキストを current にし直す。**

### F. 同時に決めたこと

- 出力テクスチャの release コールバックでは GL を呼ばない（地雷2）。sync は slot に預け、次のフレームで自分のコンテキストが current のときに消す。窓が unrealize された後だけは、コンテキストを切り替えて消し、元の current に戻す。
- 行の向き: すべてのテクスチャを「行 0 = 画像の上」で扱う（`GdkGLTexture` の表示の向き、メモリ画像のアップロードの向きと同じ）。反転はどこにも要らなかった（S1 の画面で確認）。
- X11 の既定のレンダラは GL（Wayland は Vulkan）。GL の経路の確認は X11 でもできる。

## 追記2: 影が強い・縁がジャギーになる件（2026-09-24）

ユーザーの確認（S1 を実機で操作）: スクロール追従・リサイズは正常。ただし **(a) 影が強い（拡張より強く感じる。アプリ内のボタンならもっと弱くてよい）**、**(b) 縁の付近のジャギーが多く、縁の見た目が拡張より悪い**。

### A. 切り分け

| 仮説 | 確かめ方 | 結果 |
|---|---|---|
| GTK が合成を線形光で行っている（縁の半透明の混ざり方が変わる） | 白の上に 50% の黒を GSK で描いて画素を読む | **128**（sRGB 空間の合成。線形なら 188）→ Cogl と同じ。**否定** |
| 取り込みの解像度（GTK に半解像度で描かせている） | `--capture-full`（拡張と同じ「全解像度で取り込み → GL で 2x2 ボックス縮小」）と画素比較 | 差は最大 7/255・平均 1/255 未満。見た目は同一。**否定** |
| 影の式・影の余白が拡張と違う | 拡張のコードを確認 | dock/menu/notification/OSD/QS は `shadow_max_radius = 180`、式も同じ。**同じ** |
| 1 画素 1 サンプルの評価によるエイリアス | 4x の拡大で縁を観察し、RGSS 4 サンプルと比べる | リム線（幅 1px ほどのフレネル項）が丸い端で段々になり、レンズの畳み込みで点状のノイズが出る。4 サンプルで消えた。**これが主因** |

### B. (b) 縁のジャギー — 原因と修正

`glass.frag` は照明とレンズを 1 画素 1 回だけ評価する。リムのフレネル項は幅 1px ほどの線になり、レンズは縁の数 px に背景を畳み込む。
どちらも画素より細かく変化するので、曲率が大きい（半径が小さい）ほど段差が出る。
拡張のドック（半径 30）やメニュー（半径 60）より、アプリ内のカプセル（半径 20〜26）の方が目立つのはこのため。
さらに、濃い影の本影が縁に濃い輪を作り、段差を強調していた。

**修正: スーパーサンプリング（RGSS 4 サンプル）。** `glass.frag` は 1 行も変えていない。
`cogl_prelude.glsl` で `#define main glass_reference_main` として元の `main()` を普通の関数にし、`cogl_postlude.glsl` の新しい `main()` が
`cogl_tex_coord_in` を 1/4 画素ずつずらしながら 4 回呼んで平均する（出力は事前乗算なので単純平均でよい）。
**各サンプルは拡張の式そのもの**なので、見た目の設計は変わらず、画素より細かい変化が正しく平均される。

コスト（スクロール中、パネル 2 枚）: CPU は変化なし。GPU busy% は 8% → 9〜10%。静止中は描き直さないので 0。既定 ON、`S` キーまたは `--no-supersample` で比較できる。

### C. (a) 影 — 修正

式は拡張と同じ。値が「壁紙の上に浮くドック・メニュー」向けなので、明るい窓の中の小さな部品では強すぎる。
アプリ内の既定を**半径 16・強さ 0.20**に下げた（比較画像で 30/0.55・20/0.30・16/0.20・12/0.14 を並べて選んだ。ユーザーの最終判断はデモの Lab で行う。設計書 §20 C2）。
`H` キーで拡張の値と切り替えられる。

### D. 教訓

- 「拡張より悪い」と言われたら、まず**パイプラインの差**（取り込み・合成空間）を画素で否定し、残った差を**形状と内容の差**として扱う。今回は同じシェーダでも、半径が小さいほどサンプリングの不足が表に出た。
- 元のシェーダを変えずに品質を上げるなら、**呼び出し側（サンプリング）で直す**。`#define main` による包み込みは、S5 の Core でも同じ形（`glass_main(uv)` を複数回呼ぶ）にする。

## 追記3: S5 シェーダ Core の切り出し（2026-09-24）

### A. 結論

`shaders/reference/glass.frag`（拡張の出荷版）を `shaders/core/` に切り出した。
参照シェーダと Core を、同じ入力でヘッドレスの EGL で描き比べた。
10 通りの設定 × 4 形状 × 5 背景の**全 200 ケースで、差は 0/255（ビット単位で一致）**だった（`tests/golden/glass-golden.c`、`meson test` の `glass-core-golden`）。

テストが空振りしていないことも確かめた。レンズの定数 `EDGE_LENS_FALLOFF` を 2.4 → 2.5 に変えると 200 中 141 ケースが失敗し（最大 52/255）、戻すと 0 に戻る。

### B. Core にしたときの変更（見た目を変えない変更だけ）

| 参照シェーダ | Core |
|---|---|
| `dock_x/y/w/h` ＋ `padding` ＋ `isDock` | `glass_rect`（正確な形の矩形）。余白や縮小は呼び出し側で計算する |
| `gradientStep(resolution)` = clamp(min(res)/560, 0.45, 1.2) | uniform `gradient_step` |
| 変位の上限 0.30 × min(res) | uniform `max_displacement_px` |
| `EDGE_LENS_REACH`（96px）・フットプリントの上限（64px）は固定 | 同じ定数 × `lens_px_scale`（参照 = 1。glass-lib は HiDPI で論理サイズを保つためにデバイスのスケールを渡す） |
| `stabilizedUV()` は FBO の端の 3% で屈折を弱める | `edge_damping` が 1 のときだけ（参照と同じ）。glass-lib は 0（出力はガラス＋余白だけなので） |
| マルチ領域（Quick Settings）・パネルの塗り・未使用の uniform | 削除（v2 の融合と一緒に作り直す） |
| `debug_view` 1・2 | 同じ。3（レンズの変位の可視化）を追加 |
| `cogl_sampler1`・`texture2D` | ターゲットが `GLASS_SAMPLE(uv)` を定義する |
| `main()` | `vec4 glass_shade(vec2 uv)`。ターゲットの `main()` が呼ぶ（スーパーサンプリングは 4 回呼ぶ） |

式とその順序は変えていない。等価性の根拠は 200 ケースの 0/255。

### C. S1 での確認

S1 の既定を Core（glass-lib と同じ写像: 出力テクスチャ = 面、仮想キャンバスなし、`edge_damping` 0）に切り替え、`--reference`（`R` キー）と比べた。
差のほとんどは 0〜1/255 だった。1/255 はディザで、画素の位置から乱数を作るので、写像が違うと値が変わる。
数百画素だけ最大 11/255 の差が出たが、場所は下側の内縁に沿った細い線と上側の点だった。

これは参照シェーダ自身の**不連続**で起きている。レンズの取り込みの幅が 2px を超えたところで、背景のタップが 4 → 10 に**段で切り替わる**（`footprintPx > 2.0`）。
座標系が違うと丸めが変わり、この線の位置がわずかにずれる。見た目は同じ。
- 観察: この段の切り替えは、高コントラストの背景では細い線として見える可能性がある（縁のジャギーの一因かもしれない）。スーパーサンプリングで和らいでいる。直すなら見た目の変更になるので、ユーザーの判断を仰ぐ（未着手）。

性能は変わらない（スクロール中 1.4〜1.5 ms/frame、60fps）。

### D. ビルドの仕組み

- `#include` は `tools/glsl-include.py` がビルド時に展開する（`shaders/meson.build`）。生成物は `build/shaders/glass-core.frag` と `glass-reference.frag`。
- `meson test` に `glslangValidator` の検査（Core・参照・quad を、GLES 3.00 と GL 3.30 のそれぞれで。計 6 件）とゴールデンテストが入っている。
- ゴールデンテストは Mesa の surfaceless EGL を使う。使えない環境では 77（skip）を返す。

## 追記4: アプリ内のガラスの縁を細く・鋭くする（2026-09-24）

### A. ユーザーの指摘

「端の見た目が気に入らない。拡張の方を見たら同じ感じだが、ガラスが大きいので気にならないだけだった。ウィンドウ内のウィジェットの方は、もう少し端を鋭く・すっきり・細くしてほしい」。

### B. 原因

縁の見た目を作る値は、すべて大きなガラスに合わせた**絶対 px** になっている。

| 要素 | 拡張の値 | 高さ 44px のカプセルでの割合 |
|---|---|---|
| 輪郭のぼかし（`edge_smoothing`） | ±2px（幅 4px） | 約 9% |
| リムの光の帯（`rim_width`） | 5px | 約 11% |
| 内側の影（`ao_radius`） | 7.5px | 約 17% |
| レンズの帯 | 角の半径全体（= 高さの半分）に広がる | 50% |

重なると、縁が高さの 1/5 ほどの「太くて濁った帯」になる。拡張のドックやメニューでは、同じ px でも全体に対して細いので目立たない。

### C. 修正: 同じシェーダ・同じパラメータで、アプリ内用の値を選ぶ

シェーダ（Core）も設定の種類も変えず、値だけを変えた。試作に**スイープ**機能（`--sweep`）を足した。1 つのプロセスの同じ窓の中で候補を順に当てて、パネルの周りを切り出して保存する（窓の大きさが実行ごとに違うと比べられないため）。7 候補を 3 種の背景で並べ、プリセットを決めた。

| パラメータ | extension | **thin（アプリ内の既定・提案）** | thinner |
|---|---|---|---|
| `edge_smoothing` | 2 | 1 | 0.75 |
| `rim_width` | 5 | 2.5 | 2 |
| `rim_power` | 6 | 9 | 9 |
| `ao_radius` / `ao_intensity` | 7.5 / 0.25 | 3.5 / 0.10 | 3 / 0.10 |
| `chroma_strength` | 1.5 | 1.0 | 0.8 |
| `profile_shape_n` | 7 | 14 | 24 |
| `displacement_scale` | 78.5 | 45 | 30 |
| `max_z` | 25 | 18 | 14 |

- `profile_shape_n` を上げると、ドームが四角くなる。斜面、つまり屈折が外周の数 px に集まり、レンズの帯が細くなる。`displacement_scale`・`max_z` を下げると、その細い帯での折り返しが減る。
- `thinner` は最も細く鋭いが、レンズがほとんど消えて平らなガラスに近い。
- 比較画像: `~/glass-lib-edge-presets.png`（extension / thin / thinner × 4 背景）。

**その後（2026-09-25）**: ユーザーの判断は「縁は thinner がよいが、ガラス感は残してほしい」。あわせて、thin では屈折した細かい模様が縁でジャギーになる、という指摘があった。→ [追記5](#追記5-屈折した模様が縁でジャギーになる件とガラス感2026-09-25)。プリセット `thin` は廃止した。

## 追記5: 屈折した模様が縁でジャギーになる件と、ガラス感（2026-09-25）

### A. ユーザーの指摘

1. 縁は `thinner` がよいが、ガラス感は残してほしい。
2. `thin` では、縁の近くで屈折した細かい模様（市松など）がジャギーになって美しくない。
3. スーパーサンプリング（4x）がある方がジャギーは少ない。
4. ぼかし半径の既定をもう少し小さく。

### B. ジャギーの原因（地雷9）

1 次元の数値モデル（縁からの深さごとの変位 `D`・写像の傾き `|ds/dx|`・参照の見積もり `footprintPx`）で調べた。高さ 52px のカプセル、`thin` の値の場合:

| 縁からの深さ | 変位 D | 実際の傾き（1 画素が元の何 px を覆うか） | 参照の見積もり |
|---|---|---|---|
| 0〜1px | 64〜71px | 3〜6 | 19〜22（大きすぎ） |
| 1.5px | 40px | **約 50** | 11 |
| 2px | 12px | **約 43** | 3.4 |
| 3px 以降 | 3px → 0 | 1 前後 | 1 未満 |

- 縁のすぐ内側に「崖」がある。ドームの斜面が急から平らに変わる所で、変位が 1px の間に 60px ほど落ちる。拡張の値でも同じで、崖が少し深い（2〜5px）だけ。
- 参照の見積もりは「生の変位が斜面（角の半径）全体でゆっくり変わる」前提なので、崖では 4〜15 分の 1 に小さい。10 本のタップが崖の一部しか覆わず、隣の画素（特に丸い端に沿った画素）が無関係な場所を拾う。
- 縁ちょうど（d = 0）では、`getDisplacement()` が外側で 0 を返すので、屈折が 70px 先から 0 へ**不連続**に落ちる。そこは輪郭のぼかしで α が 0.5 前後の所なので、4 サンプルでは段々になる。

256 サンプルを正解にして、画素ごとの最大誤差を測った（ぼかし半径 2、市松・縞の上、3 つのプリセット）:

| 方法 | 最大誤差（/255） | GPU busy（スクロール中、2 枚） |
|---|---|---|
| 1 サンプル | 約 100 | – |
| 4 サンプル（これまでの既定） | 39〜63 | 基準 |
| 縁の帯だけ 16 サンプル | 13〜16（正解 gt1 比）／ 22〜30（gt2 比） | +3pt |
| 縁の帯だけ 32 サンプル | 7〜8（gt1 比） | +7pt |
| **4 サンプル＋測ったフットプリント（採用）** | **14〜26（gt2 比）** | **+1pt** |

誤差は深さ 0〜3px（拡張の値では 0〜5px）に集中し、それより内側は 1 以下（ディザ）。

正解画像について（地雷11）: 最初は参照のまま 256 サンプルで正解（gt1）を作ったが、参照の見積もりは縁の外側 1.5px で大きすぎて、そこを ±9px ぼかしている。測ったフットプリントを小さい幅（1/32px）にして 256 サンプルで作り直した正解（gt2）と gt1 の差は、その帯で 22〜38 あった。採用した方法は gt2 に近い（縁が参照より少しくっきりする）。

### C. 修正: Core の「測ったフットプリント」（`lens_footprint_px`）

`glass_shade()` の中で、サンプルごとに自分のフットプリント（レンズの方向に ±`lens_footprint_px`）をレンズに通して追う:

1. 両端がどこに着地するかを計算する（`lensDisplacementPx()`。メインの計算と同じ手順）。
2. 両端の着地点が「タップの間隔」（ぼかしたテクスチャの 2 テクセル）より離れているか、フットプリントが縁をまたぐときだけ、4 等分した途中の 3 点も着地させ、その折れ線に沿って背景を平均する（`sampleBackdropPath()`。各区間 1〜8 タップ、2 テクセルおき）。ぼかしの σ は最小でも 1 テクセルなので、2σ おきのタップで平均の誤差は約 1%。
3. 縁をまたぐときは、内側の部分（上の折れ線）と外側の部分（屈折しない背景）を、フットプリントに占める割合で混ぜる。これで d = 0 の不連続が滑らかになる。
4. 変位が 0.5px 未満の所（内側）では何もしない。

- `lens_footprint_px = 0` なら参照とまったく同じ経路（ゴールデン 200 件で 0/255 のまま）。glass-lib はサンプル間隔の半分を渡す（4 サンプルなら 0.25、1 サンプルなら 0.5）。
- コストの内訳: 両端の計算はほぼ 0。コストは崖の画素の長いタップのループ（GPU は同じ波面の画素が最長のループを待つ）。タップを 1 テクセルおき・区間 16 本 → 2 テクセルおき・8 本にして、+2pt から +1pt に減った。誤差は変わらなかった。
- フットプリントの幅を 0.375・0.5px に広げても誤差は変わらない。残りの誤差は崖の中の非線形（1 区間の中で写像が曲がる）と、丸い端の接線方向（最大 1.7 倍の縮小）。

### D. 取り込み範囲（地雷10）

`thin` の値で縁の変位は約 70px、高さ 52px のカプセルでは反対側の縁の先 18px を読む。取り込みは「パネル＋ぼかしの 3σ＋2px」（ぼかし 2 なら 8px）だけだったので、長い辺の縁の帯は、取り込みの縁で固定された色の筋になっていた（茶・青のまだら）。取り込み範囲に `max(0, 96 − min(w, h))`（論理 px）を足した。取り込みの面積は増えるが、CPU は 1 フレーム 1.5〜1.9ms（パネル 2 枚）で基準（3ms）の内。

### E. ガラス感: 縁の「線」と「レンズ」を分ける

`thinner` が平らに見えるのは、レンズ（背景が縁の近くで曲がる帯）を外周 2px に押し込めているから（`profile_shape_n` 24）。縁の太さの印象は、主に線の要素（輪郭のぼかし・リムの光の帯・内側の影・色のにじみ）から来ている。そこで、線は `thinner` の値にし、レンズは拡張のドームの形（`profile_shape_n` 7）のまま強さだけを変えた。

| プリセット | 線 | `max_z` | `displacement_scale` | 見た目 |
|---|---|---|---|---|
| **`crisp`（既定・提案）** | thinner と同じ | 20 | 60 | 縁の 5〜10px で背景がはっきり曲がる |
| `crisp-strong` | 同上 | 25 | 78.5 | 拡張と同じレンズ |
| `crisp-soft` | 同上 | 14 | 45 | 弱いレンズ |
| `thinner` | 同上 | 14（n = 24） | 30 | レンズがほぼない |
| `extension` | 拡張 | 25 | 78.5 | 拡張そのまま |

線 = `edge_smoothing` 0.75、`rim_width` 2、`rim_power` 9、`ao_radius` 3、`ao_intensity` 0.10、`chroma_strength` 0.8。

### F. ぼかし半径

アプリ内の既定を 5 → **3** にした（半径は元の画素での σ）。試作の `B` キーで 2〜5 を切り替えられる。

### G. 比較画像

- `~/glass-lib-edge-presets-2.png`: 5 つのプリセット × 3 背景（ぼかし 3）
- `~/glass-lib-edge-jaggies.png`: 同じ `thin` の値で、これまでのサンプリングと新しいサンプリング（丸い端を 6 倍に拡大）
- `~/glass-lib-blur.png`: ぼかし 2〜5

**決定（2026-09-25、ユーザー）**: `crisp-soft`・ぼかし 2px・測ったフットプリント・スーパーサンプリング 4x を既定にする。ライブラリの材質 `REGULAR` の値になった（`spec/params.json`）。

### C. 調べたこと（GPU 時間は `GLASS_DEBUG=gpu-time`: `GL_EXT_disjoint_timer_query` でパスごとに測り、2 秒ごとにログへ）

- 1 フレームの GPU: ページのヘッダーのカプセル 1 枚 約 0.16〜0.18ms × 7、サイドバーのパス 約 1.4ms、ぼかしは合わせて 0.2ms 弱。780M は軽負荷の間 800MHz のまま。
- `glFinish` で先に GPU を空にしてから取り込むと、ページの取り込みの待ちは 0、サイドバーの取り込みの前の待ちは約 1.0ms（ページのパスの分。地雷20）。
- カプセルのパスの中身（1 枚あたり）: スーパーサンプリングなし 0.058ms、測ったフットプリントなし 0.07〜0.09ms、経路の色収差なし 0.12ms、経路のテクスチャ読み出しなし 0.14〜0.16ms、全部あり 0.18ms。
  → 時間の大半は縁のレンズの帯の「4 サンプル × 経路」で、読み出しよりも計算。
- 効かなかったもの:
  - パスごとの `glFlush` をやめて、ビューの終わりに 1 回（残した。カーネル呼び出しが減るだけで時間は同じ）。
  - パスを 1 枚の FBO に並べる、同じ描画を繰り返す: 描画同士は重ならず（GPU は埋まっている）、時間は比例した。
  - 平らな内側だけ 1 サンプル（差 2/255 以内）: 時間は同じだった（重いのは縁の帯）。**付録 B の方針 2（平坦部を落とさない）に反するので戻した。**
  - 経路のテクスチャ座標の変換を前もって計算する: 変わらなかったので戻した（丸めの差が出るため）。
- 効いたもの（見た目は同じ）:
  - `sampleBackdropPath` を色収差の 3 チャンネルで 1 回の歩みにまとめた（`sampleBackdropPathRGB`）。チャンネルごとの和は 3 回呼ぶのと同じ演算。カプセル 0.18 → 0.16ms、サイドバー 1.44 → 1.35ms。アプリの画面で差 0（全画素一致）。
  - Core に「輪郭の外は影だけ」の早期脱出（被覆 0 の所は、下の式に 0 が掛かるので同じ結果）。ゴールデン 0/255。時間はほぼ変わらない（残しても害はない）。
- 取り込みの読み出しの形式は RGBA8 の事前乗算で、要求と同じ（変換なし）。スクロール端の効果（GSK の blur）の取り込みでの分は約 0.35ms。

### D. 残り（相談中）: ビューをまたぐ取り込みの共有

- 試した方法: 内のビュー（ページ）の 1 回の描画で、外のビュー（スプリットビュー）のサイドバーの取り込みも描き、外のビューはノードの木を調べて「内の背景がそのまま見えている」ときだけ使う。

  つまり外のビューの取り込みは内のビューのガラスの完成を本当に必要としている。コードは外した（スクラッチに保存）。
- 上限の見積り: サイドバーの取り込みを省くと（計測用）1.8ms/フレーム。
- 案: 内のビューの 1 回の描画で「内の背景」と「内の前景だけ（透明の上）」を別々の領域に描き、外のビューの取り込みは GL で「背景 → 内のガラスの出力 → 前景」の順に重ねて作る（§6.7 の層の合成をビューをまたいで行う）。
  外のビューはノードの木で並び（背景の子 → ガラスのテクスチャ → 前景）を確かめ、違えば今どおり自分で取り込む。見積り 2.2ms 前後。設計の変更（§8.2・§6.7）なので、実装の前にユーザーと相談する。

## 追記8: 古いままの上のガラス、ドラッグ、融合の形（2026-09-25）

ユーザーの指摘（動く背景の上で確かめたもの）と、その直し方。

### A. 上のガラスが古いまま（地雷24）

- 症状: 「ガラスの上のガラス」の上のガラスが、ホバーなどで描き直されるまで、下の変化に追従しない。Playground の材質などの `GlassToggleGroup`（同じビューの層 1）は正しく追従する。
- 原因: 追従しないのは、スイッチ・スライダーのつまみ（**別の `GlassView`** の中の `GlassPanel`）。外のビューはカードのガラスを毎フレーム描き直すが、GTK はスイッチの描画ノードをキャッシュしているので、中のビューの snapshot が呼ばれない。
  同じ理由で `GlassDialog` も古いままだった（ダイアログのホストは中身だけを描き直す）。赤から青に変わる背景で確かめると、ダイアログは赤いままだった。
- 直し方:
  - 入れ子のビュー: `root` のときに外側の `GlassPanel` に自分を登録し、パネルの出力（`glass_panel_set_output`）が変わったら `gtk_widget_queue_draw()` する。
    これは外のビューの snapshot の中で起きる。GTK 4.22 の `gtk_widget_do_snapshot()` は `draw_needed = FALSE` をクラスの snapshot の**後**で行うので、伝播は描いている最中のビューで止まり、
    続けて描かれる overlay の子孫が描き直される。同じフレームで、余分なフレームは起きない（`gdk_surface_queue_render` まで伝わらない）。
  - ダイアログ: 表示中はフレームクロックの `before-paint` で `gtk_widget_queue_draw()`。PAINT の前に要求するので同じフレームで描かれる。後ろが変わっていなければ取り込みとパスはキャッシュに当たる。
    何も変わらない間はフレームが来ないので続かない（止まっている 1 秒のフレーム数 0 を確認）。
  - ポップオーバーは前からの方式のまま（親の窓の `render` で描き直す。別のサーフェスなので 1 フレーム後）。
- 確かめ方: `tests/test-widgets.c` の `/widgets/nested-view-redraw`・`/widgets/dialog-redraw`（背景だけを描き直したフレームと、全部を描き直したフレームがバイト単位で同じ）。直す前のコードでは 2 つとも失敗することも確かめた。

### B. Playground のドラッグ（地雷25）

- 症状: ドラッグしたパネルがポインタに追従しない（方向は合うが量が足りない）。ドラッグ中にガラスが 2 か所の間を高速に往復する。
- 原因: `GtkGestureDrag` の `drag-update` のオフセットは、パネル自身の座標での値。パネルは余白（margin）で動かしているので、次のレイアウトの前に来たイベントと後に来たイベントで基準がずれる。
  オフセット − 移動量 で置き直すことになり、正しい位置と元の位置の間を行き来する。
- 直し方（デモ）: ポインタの位置を、動かないステージ（`GlassView`）の座標に `gtk_widget_compute_point()` で移してから差を取る。

### C. 融合の形（地雷26）

- 症状: `GlassGroup` のボタンの隙間を 0 にしても、1 つのカプセルにならず波打つ。
- 原因: smin のふくらみは k/4 まで。接した 2 つの円の間の谷（接点での幅 0）は埋まらない。
- 直し方: 隙間が k/2（smin の首がつながり始める距離）より近い 2 つの形の間に「橋」を足した。一方の形をもう一方の位置まで動かした軌跡
  （中心を結ぶ線への射影 t で、中心・半分の大きさ・角の半径を補間した角丸矩形。並んでいれば 2 つの凸包そのもの）を、隙間に応じて (太い方の半分の幅 + 2px) × smoothstep で内側に縮める。
  隙間 0 では硬い min でつなぎ（凸包そのもの＝カプセル）、つなぎ目のなめらかさ（smin の幅）は途中で最大の k/2、両端で 0。k/2 で首が切れるのは smin と同じなので、切れる瞬間に形が跳ばない。
- 結果（スクリーンショット）: 隙間 0 で 1 つのカプセル、2〜4px でくびれ、6〜8px で細い首、12px で離れる。

### D. そのほか

- 影の強さの既定を 0.07 に（3 つの材質すべて。Lab のスライダーは明示の値としてすべての材質に効くので、Lab で 0.07 にしたときと同じ見た目になる）。
- スイッチ・スライダーのつまみの既定のぼかしを 0 に。材質を増やさず、パネル自身の既定値（非公開）として持つ。値の決まり方は「明示 → パネル自身 → 材質 → 既定」（設計書 §11.2）。
- デモ: 動く背景の再生／一時停止と速度（Playground・Controls・Lab）。`GLASS_GALLERY_PATTERN` が Controls と Lab にも効くようにした。
